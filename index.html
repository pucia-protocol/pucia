PUCIA

Universal Protocol for the Configuration of Artificial Intelligences

An open protocol that lets artificial intelligences publish, validate, certify and reuse specialised configurations, instead of starting every training run from scratch.

Read the white paper Get version 1.5

A fixed base, configurations that change everything

Ever more parameters: until when?

The current race in artificial intelligence rests on a single recipe: ever more parameters, ever more data, ever more computation. The author proposes to reverse the logic: first set a parameter limit that no longer grows, then learn to configure those parameters according to the task.

The lesson of living organisms

A neuron, a liver cell and a muscle cell do not differ in the quantity of DNA they contain, but in which genes are expressed and which remain silent. For AI: a fixed number of parameters, like a genome, and a configuration that decides what is expressed.

Learn once, know everywhere

The learning effort is made once, then shared: loading a validated configuration instead of repeating the training. Knowledge produced once and shared by all.

What PUCIA adds

Adapter transfer is already practised. What is missing is what turns a configuration into a certified asset, not merely a shared file:

  • a signed and timestamped manifest;
  • reproducible independent validation;
  • complete accounting of costs and parameters.

Where it stands

The protocol distinguishes three regimes, and says plainly which one is within reach.

RegimeWhat it meansStatus
R1Load an existing configuration or adaptation.Feasible today, subject to compatibility.
R2Change speciality without increasing the declared total parameter budget.Experimental.
R3Generate a high-performing configuration for a new task without massive task-specific training.Advanced hypothesis; first research results published (Text-to-LoRA).

What is not established

LoRA usually adds parameters. It can serve as a reference for a prototype but does not demonstrate the strict ceiling. Neither universal weight compatibility nor the instant programming of new competences has been achieved.

Five falsifiable hypotheses

PUCIA is a research, standardisation and economic value proposal, to be validated by experiment. Each hypothesis comes with the test that could refute it.

HypothesisRefutation test
H1A validated configuration can be reused at a lower marginal cost than retraining.Compare full costs, including integration and validation, at equal quality.
H2A fixed-budget model family can serve several tasks through reconfiguration.Compare with a single-task baseline and check the total budget.
H3Pooled configurations improve the prediction of new configurations.Evaluate out of distribution on isolated tasks.
H4Cooperating AI agents improve the search for configurations.Compare cooperation, a single agent and conventional search at equal computation.
H5A public standard and a configuration market create economic incentives.Commercial pilots with observed costs and revenues.

Rule: pre-registered metrics, reproducibility and honest cost accounting.

Verify a package yourself

The repository holds the white paper, the draft standard PUCIA-0001 (configuration package and manifest format), its normative JSON schema, a reference verifier and a signed example package. Three steps check the example:

  1. Get the repository.
  2. Install the two dependencies.
  3. Run the verifier on the example package.
git clone https://github.com/pucia-protocol/pucia.git
cd pucia
pip install jsonschema cryptography
python verify.py exemple-masque-extraction pucia-0001-manifest.schema.json

Expected result

CONFORME PUCIA-0001 (contrôles V1 à V9)

The verifier answers in French: “conformant with PUCIA-0001, checks V1 to V9”. This result attests the structure of the package, the integrity of its content and the presence of the timestamp proofs. The cryptographic validity of the proofs falls under PUCIA-0002, and the identity of the publisher under PUCIA-0003.

How to check the proof yourself

An open project with a single maintainer

AI agents propose, test, validate and improve configurations autonomously, within an enclosure whose ceilings are set in advance. A human maintainer alone decides what enters the standard, and a legal entity carries the contracts and the financial flows.

The four gates reserved for the human

  1. Integration into the standard. The maintainer alone decides what enters the specification and the official catalogue.
  2. Money and contracts. An AI agent has no legal personality: licences, sales and payments are concluded by the operating legal entity, Pixel AI SARLU.
  3. Ceilings. The maintainer sets the computation, storage and spending budgets in advance; any overrun automatically suspends the activity concerned.
  4. Release into the real world. No configuration propagates automatically from one AI to another outside the enclosure.
